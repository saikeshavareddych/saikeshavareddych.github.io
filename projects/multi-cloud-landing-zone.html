The problem

Every team wanted its own place to deploy, and wanted it without filing a ticket. The straightforward answer is to build a landing zone. The trap is building two of them.

When AWS and Azure each get their own tooling, their own guardrail definitions and their own onboarding path, the two estates drift within a quarter. One cloud becomes the real one and the other becomes the one nobody patches. I wanted a single set of definitions where adding a guardrail meant adding it once.

Constraints

  • No shared network between clouds. No VPN, no ExpressRoute. Identity federates, packets do not.
  • Identity cannot be duplicated. One source of truth for who a human is, with cloud roles derived from it.
  • Every environment must be destroyable and rebuildable. If I cannot tear it down and get it back, it is not infrastructure as code, it is a pet.
  • Cost attributable per team on day one. Tagging retrofitted later never happens.
  • No long-lived cloud credentials anywhere. Including in CI.

Architecture

One Terraform repository, two providers, and a shared control plane that both sides report into. The cloud-specific parts follow each cloud's own idiom rather than forcing a common abstraction: AWS gets Organizations with Control Tower guardrails and a transit-gateway network account, Azure gets management groups with Azure Policy and a hub VNet with firewall egress. What is shared is the layer above: state, policy, drift detection, cost and break-glass.

Decisions and trade-offs

Every one of these had a cost. Listing the cost is the point.

DecisionWhyWhat it costs
Terraform for both, not CloudFormation plus BicepOne language, one review process, one set of reviewers. Module authors do not have to be bilingual.Gives up native per-cloud niceties like CloudFormation rollback and Bicep's what-if fidelity.
State split per cloud and per environmentA bad apply in dev cannot reach prod, and a lock held by one pipeline does not stall the others.More wiring, and cross-stack references have to go through data sources instead of direct outputs.
OPA with Conftest rather than a paid policy enginePolicies run identically on a laptop and in CI, so a violation is found before the pull request exists.No native integration with the Terraform Cloud run pipeline; the gate is something I have to wire and maintain.
OIDC federation from CI to both cloudsThere is no credential to leak, rotate, or find in a git history two years later.The trust policy has to be scoped to the exact repository and branch. Scoped loosely, it is worse than a static key, because it looks safe.
Per-cloud network idioms, not a unified abstractionHub-and-spoke on Azure and transit gateway on AWS are each the well-trodden path, with the documentation and failure modes to match.Two mental models for anyone reading the code. I decided that was cheaper than one leaky abstraction over both.

What it achieves

These are design targets the build is measured against, not business outcomes claimed on someone else's behalf.

  • A new environment on either cloud comes up from an empty state in about twelve minutes.
  • Policy violations surface at terraform plan, before review, not after apply.
  • No static cloud credential exists in the system. Every identity is short-lived and federated.
  • A scheduled plan runs daily against every workspace, so drift is a notification rather than a discovery during an incident.
  • Full teardown and rebuild is exercised deliberately, because a recovery path that is never run is a recovery path that does not work.

What I would change

I built generic modules first and composition roots second, which is backwards. The modules grew configuration options to serve environments that did not exist yet, and half of those options were never set to anything but the default.

Next time I would write three concrete environments with duplication, let the real shared shape emerge, and only then extract modules. The duplication would have been cheaper than the abstraction I guessed at.
