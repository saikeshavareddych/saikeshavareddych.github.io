The problem

Releases depended on a person opening the portal and clicking through in the right order. It worked, because the person was careful. It was not repeatable, there was no rollback beyond redeploying the previous build and hoping, and the approval trail lived in a chat thread.

The goal was a release that a new joiner could run on their second day, and a rollback that took one action rather than a rebuild.

Constraints

  • Approvals must be recorded against the deployment, not in chat.
  • Secrets cannot live in pipeline variables. Pipeline variables end up in logs, in forks, and in screenshots.
  • Zero downtime during cutover, including for connections already in flight.
  • Rollback must be a single action and must not require a build.
  • Pipeline definitions must be shared, so a fix to the build process reaches every service.

Architecture

Azure Repos with branch policy on trunk feeds YAML pipelines built from templates held in a central repository. Builds push signed, scanned images to Azure Container Registry. Deployment runs through Azure DevOps environments, which carry the approval gates and keep the audit trail attached to the deployment record.

In the cluster, an application gateway ingress terminates TLS in front of blue and green deployments. Secrets are mounted at pod start through the Key Vault CSI driver, and pods authenticate to Azure with workload identity, so nothing sensitive is ever written into a pipeline variable or a Kubernetes secret that outlives the pod.

Decisions and trade-offs

Every one of these had a cost. Listing the cost is the point.

DecisionWhyWhat it costs
Blue-green rather than a rolling updateThe candidate is fully deployed and verifiable before it takes traffic, and rollback is a weight change rather than a redeploy.Requires roughly double capacity during cutover, which costs real money on a large service.
Key Vault CSI driver instead of pipeline variables or sealed secretsThe secret is fetched at mount time by an identity the pod owns. It never exists in CI, in git, or in etcd.Pod startup now depends on Key Vault being reachable. A Key Vault outage becomes a scheduling outage.
Workload identity instead of service principal secretsNothing to rotate, and the credential is bound to the pod's service account rather than shared across a namespace.Requires the cluster's OIDC issuer to be configured correctly up front, and the failure mode when it is not is an unhelpful token error.
Central pipeline templates, versioned and referenced by tagA fix to the build process reaches every service. Services pin a tag, so the fix arrives when they choose.The template repository becomes a bottleneck and a single point of failure. It needs the same review rigour as production code.
Hold for ten minutes on burn rate before shifting trafficCatches the failures that only appear under sustained real traffic, which are the ones that matter.Ten minutes is a long time to hold a cutover for a small service. This should scale with the service, and currently does not.

What it achieves

Measured as design targets for the build:

  • A release is one pipeline run with a recorded approval, repeatable by anyone with permission.
  • Rollback is shifting ingress weight back to blue. It takes seconds and requires no build.
  • No secret is present in a pipeline variable, a repository, or a long-lived Kubernetes secret.
  • The approval trail lives with the deployment record and survives the chat history.
  • Cutover holds until probes and the burn-rate alert have both stayed quiet, so a slow failure blocks promotion.

What I would change

The fixed ten-minute hold is the weakest part of the design. For a service handling meaningful traffic it is barely enough; for a low-traffic internal service it is ten minutes of waiting for a signal that statistically cannot arrive in that window.

The hold should be derived from how long it takes that specific service to accumulate enough requests to detect a regression. I used a constant because it was easy to reason about, and it is the first thing I would replace.
