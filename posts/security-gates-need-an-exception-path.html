Writing / Security gates

A security gate with no way past it will be deleted

Written while building the AWS DevSecOps pipeline

The first version of my pipeline had six security gates and all of them were advisory. They ran, they produced a report, and the report went into an artifact that nobody opened. Findings accumulated for months, because nothing downstream changed behaviour based on them.

So I made them block. That part took an afternoon: change the exit code, wire it into the job's success condition, done. I felt like I had solved the problem.

Then a gate blocked a release on a Friday evening

The finding was a transitive dependency with a critical advisory and no patched version published. It was genuinely critical. It was also genuinely not exploitable in that code path, and the release had been promised.

There was no way past the gate. Not because I had thought carefully about exceptions and decided against them, but because I had not thought about exceptions at all. The only options available were ship nothing or turn the gate off.

We turned the gate off. It stayed off for two weeks, because turning it back on meant confronting the same finding again with the same lack of options. One evening cost me the gate, and the credibility to argue for the next one.

What the exception path has to do

An exception is not a bypass. A bypass is a switch that makes the problem invisible. An exception is a recorded decision that the risk is understood and accepted, by someone, until a date. The difference is entirely in the bookkeeping, and the bookkeeping is the whole point.

Four properties, and the fourth is the one people skip:

  • It names the specific finding. Not the scanner, not the stage. A blanket exception is a disabled gate wearing a lanyard.
  • It has an owner. A human who accepted the risk, recorded where the decision can be found later.
  • It expires. A date after which the exception stops applying and the gate blocks again. Without this, every exception is permanent.
  • It is visible while it is active. An exception that only exists in a YAML file nobody reads has the same practical effect as the gate being off.

I keep them in the repository, next to the code they apply to, so the exception shows up in review when someone touches that dependency. It also means the list of active exceptions is one git grep away, and an expired one fails the build the same way the original finding did.

The part I would tell myself

The exception path is not a follow-up task. It is part of shipping the gate, in the same pull request, before the gate ever blocks anything.

This generalises past security. Any control that can say no needs a documented, bounded way to say "yes, this once, and here is who decided". Controls without one do not survive contact with a deadline. They get disabled by people who are not being reckless, just cornered — and a control you removed under pressure is much harder to reinstate than one you never shipped.

Design the way past the gate at the same time as the gate. If you cannot describe the exception path, you have not finished designing the control.
